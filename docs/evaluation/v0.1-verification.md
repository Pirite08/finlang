# v0.1 구현 및 검증 결과

검증일: 2026-10-31. 환경: Go 1.25.5, Windows/amd64.

실행 파일은 build/fin.exe다. 런타임은 Go 표준 라이브러리와 프로젝트 내부 패키지만 사용한다.

## 구현 범위

원문에서 읽는 불변 Decimal, 정확한 +·-·*와 비교, 명시적 div·round, 정확한 format, let, Bool·String, if/else, fn·return, 어휘적 스코프·클로저·재귀, UTF-8 소스·위치 진단, 파일 실행, 한 줄 REPL을 구현했다. 소스·토큰·AST·평가·호출 깊이에 한도를 적용한다.

Money, settle, JSON 계약 실행, trace 기록기, COBOL 비교는 후속 범위다. Trace의 공통 타입과 선택적 인터페이스만 준비했다.

## 최종 통합 검증

| 검증 | 결과 |
|---|---|
| go test -json -count=1 -coverprofile=build/coverage.out ./... | 종료 0, 실패 0 |
| 최상위 테스트·퍼즈 함수 | 55개 통과 |
| 하위 테스트를 포함한 통과 이벤트 | 155개 |
| go vet ./... | 종료 0, 진단 없음 |
| go build -o build/fin.exe ./cmd/fin | 종료 0 |
| gofmt -l cmd internal experiments | 미포맷 파일 없음 |
| go list -m all | example.com/finlang만 표시 |
| 빌드한 실행 파일의 smoke 검증 | 9개 통과 |

테스트 함수 개수와 생성 숫자 사례 개수는 다르다. 아래의 10,000쌍과 12,041건은 테스트 함수 내부에서 반복 비교한 데이터다.

원자료는 build/test-results.jsonl, build/test-summary.json, build/coverage.out, build/smoke-results.json에 저장했다. 기본 패키지 커버리지 계측의 전체 문장 수치는 91.9%다. 다른 패키지의 통합 테스트에서 호출한 AST 등의 실행은 해당 패키지 수치에 합산되지 않는다. 커버리지 자체를 숫자 정확성의 증명으로 해석하지 않는다.

## 소수 연산의 독립 검증

### 정확한 사칙연산

시드 20261031의 입력 10,000쌍에 대해 덧셈·뺄셈·곱셈 총 30,000개 결과를 math/big.Rat과 비교했다. 유한 십진수의 허용 범위를 판단하는 테스트 기준은 유리수 분모에서 2와 5를 분해하며, 런타임의 정규화 함수를 재사용하지 않는다.

- 정확한 결과 비교: 20,835건.
- 자릿수 한도를 넘어서 거부해야 하는 사례: 9,165건.
- 기대 값 또는 오류 분류 불일치: 0건.

### 반올림과 나눗셈

Python 표준 decimal의 문자열 입력, precision=512, 명시적 반올림 모드로 독립 기준을 만들었다. Go 반올림 함수를 정답 생성에 사용하지 않았다. 먼저 손으로 정한 41개 사례를 검산하고 생성 사례를 추가했다.

| 결과 분류 | round | div | 합계 |
|---|---:|---:|---:|
| 정확한 성공 | 2,491 | 465 | 2,956 |
| 명시적 반올림 성공 | 2,652 | 4,040 | 6,692 |
| EXACT의 값 손실 오류 | 882 | 1,364 | 2,246 |
| 0 나누기 오류 | 0 | 62 | 62 |
| 숫자 한도 오류 | 0 | 85 | 85 |
| 전체 | 6,025 | 6,016 | 12,041 |

Go 결과의 값·Inexact·오류 분류가 12,041건 모두 기준과 일치했다. 별도 숫자 검토자가 정확한 Fraction 연산으로 같은 12,041건을 다시 검사했고 불일치가 없었다.

기준 파일: testdata/rounding_oracle.json.

SHA-256: 78de3a9e32db65a90492bb611670850b788674c97ae8fdcd3d598f3a1aa1b18e.

재생성 및 검증:

    python experiments/generate_rounding_oracle.py
    go test ./internal/decimal -count=1 -v

Python은 테스트 기준 생성에만 사용한다. 빌드한 인터프리터 실행에는 필요하지 않다.

## 비정상 입력

각 담당 작업에서 실제 실행한 유한 fuzz 캠페인:

| 대상 | 실행 횟수 | 결과 |
|---|---:|---|
| 숫자 파싱 | 338,823 | 통과 |
| 렉서 | 170,198 | 통과 |
| 파서 | 220,596 | 통과 |

요청 시간은 각 5초, 병렬 worker는 2개다. 입력 크기와 깊이를 제한한 캠페인이다. 숫자·렉서·파서 race 검사도 통과했다. 상세 명령은 ../development/decimal-report.md와 ../development/syntax-report.md에 있다.

## 빌드한 실행 파일 확인

실제 build/fin.exe로 다음 아홉 경로를 검사했다.

1. decimal.fin: 0.3, true, 0.30.
2. simple_interest_decimal.fin: 25000, 0.333333.
3. rounding.fin: -2, -3, -2, -2, 10.00, 1.24, 1.25.
4. REPL: 이름 유지, 0 나누기 오류 뒤 다음 정상 입력 실행.
5. 파일 슬래시 나눗셈: 정책 안내와 종료 1.
6. 닫힌 표준 출력의 REPL print: 즉시 중단, 종료 2.
7. 닫힌 표준 출력의 version: 진단과 종료 2.
8. 닫힌 표준 출력의 help: 진단과 종료 2.
9. 닫힌 표준 출력의 파일 print: 진단과 종료 2.

초기 smoke 검사 스크립트는 help/version에도 E_OUTPUT_IO 코드 문자열을 요구했다. 이 호스트 경로의 계약은 진단과 종료 2이므로 검증 조건을 수정한 뒤 아홉 경로가 통과했다. 소스 평가 중 print 실패는 E_OUTPUT_IO로 표시한다.

## 검토와 수정

숫자 검토는 명세·코드 품질 모두 승인됐다. 전체 검토에서는 출력 실패가 REPL에서 복구 가능한 언어 오류로 취급되는 문제 한 건을 발견했다. 닫힌 io.Pipe의 회귀 테스트가 먼저 실패하는 것을 확인한 뒤 오류 전파를 수정했다.

수정 후 CLI·REPL 회귀 테스트, 전체 suite, 별도 검토와 실제 실행 파일의 닫힌 출력 검사가 통과했다. 기록은 ../development/numeric-review.md, ../development/final-review.md, ../development/final-review-followup.md에 있다.

이번 검증은 정한 입력·한도·사례에서의 결과다. COBOL 호환성과 실제 금융 업무 규칙은 아직 검증하지 않았다. 초기 성능 원자료는 각 작업 보고서에 있으며 문자열 직접 산술보다 빠르다는 결론은 내리지 않았다.
