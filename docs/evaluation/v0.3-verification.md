## 명령과 원자료

실제로 구성한 GnuCOBOL 환경에서:

```powershell
New-Item -ItemType Directory -Force build | Out-Null
$env:FINLANG_REQUIRE_COBOL = '1'
$env:FINLANG_COMPAT_REPORT = Join-Path (Get-Location) 'docs/evaluation/v0.3-compatibility.jsonl'
go test -json -count=1 '-coverprofile=build/v0.3-coverage.out' ./...
go vet ./...
go build -o build/fin.exe ./cmd/fin
go test ./internal/lexer -run '^$' -fuzz FuzzLexerNoPanic -fuzztime=30s -parallel=2
go test ./internal/decimal -run '^$' -fuzz FuzzDecimalParse -fuzztime=30s -parallel=2
```

PowerShell에서는 위 coverage 옵션처럼 점이 들어간 경로를 하나의 인수로 따옴표 처리한다. 첫 통합 명령은 이 인수가 둘로 분리돼 존재하지 않는 `.3-coverage.out` 패키지 오류를 냈다. 인수 배열에서 원인을 확인하고 명령을 고친 뒤 위 전체 테스트를 다시 실행했다. 인터프리터 코드를 고친 결과가 아니다.

## 기존 기능 회귀

기존 소수 엔진의 production Go 파일·규칙·계약은 바꾸지 않았다. Decimal fuzz는 기존 함수의 파일을 옮기고 한도·비정상 입력·정규형 왕복 seed를 확장했다. CLI 버전은 v0.3.0으로 갱신했다.

전체 테스트에서 기존 `math/big.Rat` 입력 10,000쌍과 반올림·나눗셈 oracle 12,041건을 다시 실행했다. 기존 Money·통화·정산 시점·JSON·trace·CLI·REPL 검사도 함께 통과했다. 실험용 문자열 덧셈의 별도 10,000쌍은 독립 유리수 기준으로 확인했으며 런타임에 편입하지 않았다.

## 주장할 수 있는 범위

교육용 순수 계산 규칙 3개를 위 컴파일러·필드·모드·입력 집합에서 비교했다. GnuCOBOL에서 실제 확인한 표기와 예약어 차이를 숨기지 않고 프로필에 기록했다. IBM COBOL·실제 은행 소스·DB·거래 확정·권한·복구는 검증하지 않았다.

이번 덧셈 측정에서 스케일드 정수 구현의 속도 우위는 관찰하지 못했다. 사람 대상 평가도 실행하지 않았으므로 원래 설계의 사용성 원자료 완료 기준은 남아 있다. 이 두 항목을 정확한 계산 결과나 COBOL 표본 일치와 혼동하지 않는다.

독립 최종 검토에서는 새 복제본의 build 디렉터리 생성 절차와, 차등 비교 표본에 실제 포함된 합산 중간값의 표기를 보완했다. 계산 엔진이나 기준 결과를 바꾼 수정은 없었다.

[독립 최종 검토](../development/v03-final-review.md): 남은 지적 사항 없음, 통합 가능 판정. 파일 해시와 성능 원자료의 통계도 별도로 대조했다.
