# v0.2 구현 및 회귀 검증 결과

검증일: 2026-10-31. 환경: Go 1.25.5, Windows/amd64.

## 구현한 기능

- KRW·USD Money 자료형, 통화 검사, 불변 금액과 정확한 연산.
- 자리와 모드를 직접 지정하는 settle, Money div, 값 손실 없는 format_money.
- 메타데이터·입력·출력의 엄격한 JSON 계약. 금액·이율·범위는 문자열로 처리.
- 실제 평가에서 수집하는 산술·비교·조건 분기·함수 결과·정산·반올림 기록.
- 결정적인 JSONL header/event/summary와 명시적 trace_truncated.
- 파일·JSON·trace CLI 통합과 v0.1 REPL 유지.

COBOL 실행 비교와 실제 금융 운영 적합성은 이번 검증 범위에 포함하지 않는다.

## 기존 소수 연산 회귀

v0.1에서 만든 독립 기준을 그대로 다시 실행했다.

- math/big.Rat 기준 입력 10,000쌍: +, -, *의 30,000개 기대 결과/한도 거부 비교.
- Python decimal 기준 round·div 12,041건: 값·Inexact·오류 분류 일치.
- 기존 양수·음수의 절반, 자리 올림, 연속 반올림, EXACT 오류, 피연산자 보존 테스트.
- 실제 v0.1·v0.2 Windows 실행 파일로 예제 세 개의 출력을 직접 비교.

Decimal 디렉터리의 14개 Go 파일은 import 선언을 제외한 내용이 기준 커밋 8cc70ba와 동일함을 확인했다. 모듈 경로는 example.com/finlang에서 github.com/Pirite08/finlang으로 바꿨으며 숫자 엔진의 알고리즘을 수정하지 않았다.

기존 예제:

| 파일 | v0.1과 같은 출력 |
|---|---|
| decimal.fin | 0.3, true, 0.30 |
| simple_interest_decimal.fin | 25000, 0.333333 |
| rounding.fin | -2, -3, -2, -2, 10.00, 1.24, 1.25 |

보관한 로컬 실행 파일은 build/fin-v0.1.exe와 build/fin.exe다.

## Money와 정산

테스트는 같은 통화의 +·-·비교, 양쪽 순서의 Money×Decimal, Money 나눗셈, 지원하지 않는 통화, 통화 불일치, 타입 혼합, 0 나누기, 자리·숫자 한도를 포함한다.

Money 생성은 원·센트 단위로 자동 정산하지 않는다. USD 0.335 세 건에 대해:

| 정산 위치 | HALF_EVEN, 소수 두 자리 |
|---|---|
| 세 건을 합산한 뒤 정산 | USD 1.00 |
| 각 건을 정산한 뒤 합산 | USD 1.02 |

음수의 절반과 EXACT 실패, 원래 금액이 보존되는지도 확인했다. 상세 기록: ../development/v02-money-report.md.

## 엄격한 JSON 계약

확인한 경계:

- 알 수 없는 필드, 누락 필드, 중복 키와 이스케이프를 푼 뒤 같은 키 거부.
- UTF-8·바이트 길이·객체/배열 깊이·뒤따르는 두 번째 JSON 문서 제한.
- 금액·이율의 JSON 숫자 사용 거부. 중간 float64 변환 없음.
- 정규화 전의 실제 소수 자리 개수 검사.
- 계약의 순서대로 함수 인수 전달.
- 출력 타입·통화·범위·자리 검증이 끝난 뒤 정상 JSON 기록.
- 계약 오류는 위치 null, 소스 실행 오류는 안쪽 파일·줄·열 유지.

입력 0.100000000000000001은 scale_max=18인 테스트 계약에서 정확하게 보존했다. 기본 단리 계약의 연이율 입력은 scale_max=6을 따른다.

세 실제 규칙을 parser → 같은 Evaluator의 Run/Call → 계약 출력으로 실행했다.

| 규칙 | 예제 입력 | 확인한 JSON 결과 |
|---|---|---|
| interest_v1 | KRW 1000000, 연이율 0.05, 기간 0.5 | KRW 25000 |
| fee_v1 | KRW 2000000, 누진식 수수료 | KRW 1500 |
| sum_v1 | USD 0.335 세 건 합산 후 정산 | USD 1.00 |

초기 CLI 테스트의 수수료 기대값은 다른 입력 1002000의 1001을 사용했다. 실제 fixture 입력 2000000과 명세를 확인해 기대값을 1500으로 수정했으며 수수료 계산 코드는 변경하지 않았다.

상세 기록: ../development/v02-contract-report.md, ../development/v02-contract-review.md.

## 계산 기록

기록은 실행한 피연산자·결과·통화·소스 위치를 사용한다. round·div·settle에는 목표 자리·모드·Inexact가 들어간다. 조건 분기는 실제 선택한 쪽만 남기고 함수 호출에는 실제 인수와 결과를 남긴다.

확인한 항목:

- 동일 소스·입력·설정의 JSONL 바이트 일치.
- trace 유무와 작은 기록 한도에 관계없이 수치 결과 일치.
- 실제 CLI에서 10,000개를 넘는 산술 이벤트를 만들고 첫 10,000개만 보관.
- summary에 trace_truncated=true를 표시하면서 계산을 계속함.
- 입력 배열과 자리 포인터의 복사, 외부 snapshot 수정으로 내부 기록이 바뀌지 않음.
- 기록 파일 쓰기 실패 시 종료 2, JSON 정상 결과를 먼저 내보내지 않음.
- trace 대상으로 소스·계약·입력 파일을 지정하면 덮어쓰기를 거부.

상세 기록: ../development/v02-trace-report.md.

## 독립 검토와 수정

통합 검토와 별도 JSON 계약 검토를 받았다. 계약 검토는 명세·품질 모두 승인됐다. 통합 검토에서 옵션 해석 오류 한 건을 발견했다.

- 수정 전: -unknown -json은 stdout이 비었고 -json -unknown만 JSON 오류를 출력했다.
- 수정 후: 등록된 플래그의 값 소비, --, 위치 인수와 명시적 bool 값을 존중해 오류 응답 모드를 복구한다.
- 실제 CLI 회귀 테스트가 먼저 실패한 뒤 수정했고, 재검토에서 명세·품질 모두 승인됐다.

숫자로 보이는 금액 문자열의 강제 변환, 숨은 정산, 자동 환전은 추가하지 않았다. 기록은 디버깅용이며 위변조 방지 감사 시스템의 구현을 뜻하지 않는다.
