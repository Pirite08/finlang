# 금융 계산 인터프리터 최종 설계안

작성일: 2026-10-31

이 프로젝트는 금융 계산의 단위, 반올림 시점, 계산 근거가 코드에 드러나는 Go 기반 소형 언어를 만든다. 기본 인터프리터를 완성한 뒤 Money 자료형과 규칙 입출력을 추가하고, 교육용 COBOL 프로그램의 작은 계산 규칙을 같은 입력으로 비교한다.

현재 확인한 개발 환경은 Windows/amd64, Go 1.25.5이며 작업 폴더는 비어 있다. 이 문서는 개발할 동작과 평가 방법을 정한 설계안이다. 구현 결과나 성능 측정치는 포함하지 않는다.

## 1. 프로젝트의 중심 생각

설계 철학의 제안 문장은 다음과 같다.

> 돈을 다루는 코드는 금액의 단위와 반올림 근거까지 읽을 수 있어야 한다.

이 문장은 사용자의 기존 신념을 인용한 것이 아니라, 제시한 활동에서 이어갈 수 있는 프로젝트 원칙이다. 스케일드 인터저와 은행가 반올림 자체는 기존 기술이다. 이 프로젝트의 기여는 그 기술을 문법, 자료형, 오류 안내, 계산 근거, 이전 결과와의 비교에 일관되게 연결하는 데 있다.

| 원칙 | 설계로 옮기는 방법 | 확인할 증거 |
|---|---|---|
| 계산과 정산을 구분한다 | 덧셈·뺄셈·곱셈은 허용 범위에서 정확하게 계산하고, 자리 줄이기는 명시한다 | 개별 정산과 합산 후 정산의 결과 차이 |
| 값의 의미를 지킨다 | Decimal과 Money를 구분하고 통화가 다른 연산을 거부한다 | 정상 계산과 통화 혼합 오류 사례 |
| 틀렸을 때 원인을 찾게 한다 | 오류 위치, 입력값, 반올림 정책, 적용 분기를 남긴다 | 오류 수정 과제와 실제 실행에서 수집한 trace |
| 작은 규칙부터 옮긴다 | 입력과 출력이 분명한 계산 함수 하나씩 비교한다 | COBOL 기준 프로그램과의 차등 테스트 |

정확한 숫자 표현은 업무 규칙의 타당성을 대신하지 않는다. 이율의 기간, 수수료의 경계, 반올림 위치를 잘못 정하면 Decimal을 사용해도 업무상 결과는 잘못될 수 있다.

## 2. 해결할 문제와 기술 선택

| 문제 | 선택한 해결 | 남는 조건 |
|---|---|---|
| 일부 십진수를 이진 부동소수점으로 정확히 표현하기 어렵다 | 숫자 원문에서 Decimal을 직접 생성한다 | float64로 변환한 뒤 Decimal로 되돌리지 않는다 |
| 문자열 표현과 실제 산술 구조가 뒤섞일 수 있다 | 입력·출력 문자열과 정수 계수·스케일을 분리한다 | 문자열 방식과의 속도 차이는 직접 측정한다 |
| 고정 크기 정수의 범위를 넘을 수 있다 | 계수는 big.Int로 저장하고 언어 차원의 크기 상한을 둔다 | 무한 정밀도나 무한 메모리를 약속하지 않는다 |
| 나눗셈은 무한소수가 될 수 있다 | div에 결과 자리와 반올림 모드를 요구한다 | 유한 자리로 나타내는 과정의 손실을 명시한다 |
| 반올림 위치가 결과를 바꾼다 | round와 settle을 코드에 표시한다 | 업무마다 정산 정책을 지정한다 |
| 숫자만으로 통화 의미를 알기 어렵다 | Money에 통화와 Decimal 금액을 묶는다 | 환율 변환은 이번 범위에 포함하지 않는다 |
| 기존 계산의 의미를 파악하기 어렵다 | 함수·계약·경계 사례·trace를 함께 관리한다 | 문법만 바꿔 유지보수 문제가 해결됐다고 판단하지 않는다 |

검토한 접근은 세 가지다. 교재의 범용 언어에 소수 계산만 추가하면 가장 빨리 완성할 수 있지만 금융 업무에서의 선택을 드러내기 어렵다. 처음부터 COBOL 전체 호환 언어를 만들면 데이터 형식과 운영 환경까지 범위가 커진다. 이 설계는 작은 금융 계산 DSL을 만들고 순수 계산 규칙부터 비교하는 접근을 권한다.

## 3. COBOL과의 관계

### 3.1 기존 기술을 정확하게 이해한다

COBOL은 PICTURE로 자릿수와 소수점 위치를 표현하고 COMP-3/PACKED-DECIMAL 같은 십진수 저장 형식을 제공한다. 따라서 이 프로젝트를 COBOL에 없는 소수 정확성을 처음 제공하는 언어로 설명하지 않는다. [S1]

GnuCOBOL은 NEAREST-EVEN을 포함한 반올림 모드를 제공한다. 반올림을 지정하지 않은 경우, 기본 ROUNDED를 사용한 경우, NEAREST-EVEN을 지정한 경우의 동작을 서로 같다고 가정하지 않는다. [S2]

Python decimal과 Java BigDecimal도 정밀한 십진 연산과 반올림 제어를 제공한다. 비교할 때는 이 기능을 올바르게 사용한 코드를 기준으로 삼는다. [S3] [S4]

### 3.2 대체할 단위

이번 프로젝트가 옮길 단위는 외부 상태를 바꾸지 않는 계산 규칙이다. 예금 단리, 구간 수수료, 정산 시점을 정한 합산처럼 입력과 출력이 고정된 함수를 대상으로 한다.

거래 원장의 갱신, 동시 접근 제어, 권한, 거래 확정과 복구는 별도 운영 시스템의 책임이다. CICS의 작업 단위와 복구 기능은 숫자 결과 일치만으로 대체했다고 볼 수 없다. [S5]

| 단계 | 산출물 | 주장할 수 있는 범위 |
|---|---|---|
| L0 계산 언어 | Decimal, 변수·분기·함수, CLI | 명시한 계산을 실행하는 인터프리터 |
| L1 교육용 규칙 비교 | 직접 작성한 COBOL 규칙 3개와 DSL의 동일 입력 비교 | 해당 컴파일러·규칙·입력 집합에서 결과가 일치함 |
| L2 실제 규칙 병행 실행 | 제공받은 실제 규칙, 실제 조건을 반영한 입력, 차이 분석 | 평가한 업무 규칙의 부분 대체 가능성 |
| L3 운영 모듈 교체 | 업무 소유자의 검증, 운영·복구·감사·배포 조건 | 검증 범위를 갖춘 특정 모듈의 운영 대체 |

16주 기본 계획의 목표는 L1이다. 실제 COBOL 소스가 확보되면 L2를 별도 프로젝트로 평가한다. GnuCOBOL에서 교육용 사례가 일치한 사실을 IBM Enterprise COBOL이나 은행 시스템 전체의 호환성으로 확대하지 않는다.

### 3.3 이관할 때 보존할 것

- 입력 필드의 부호, 허용 범위, 소수 자리.
- 수식의 평가 순서와 값이 필드에 저장되는 지점.
- 중간 필드와 최종 필드의 자리 제한.
- 절사와 반올림 모드, 반올림 시점.
- 크기 초과·0으로 나누기·잘못된 입력의 처리.
- 적용된 수수료 구간 등 분기 결과.

새 숫자 엔진의 범위가 더 넓더라도 기존 수신 필드의 범위를 넘긴 값을 정상 결과로 바꾸지 않는다. 호환 계약에서 기존 범위를 검사하고 오류 상태를 비교한다. 기존 프로그램의 정의되지 않은 결과를 임의로 모사하지 않는다.

## 4. 단계별 완성 범위

주 6~8시간을 가정한다. 16주는 96~128시간이며, Go가 처음이거나 수치 검증에서 시간이 필요하면 2~4주의 여유를 둔다.

| 버전 | 기간 | 범위 | 완료 기준 |
|---|---|---|---|
| v0.1 계산 언어 | 1~8주 | Decimal, 반올림, let, if, fn, return, 비교, 출력, REPL·파일 실행 | 숫자 규칙과 오류 테스트를 통과하는 실행물 |
| v0.2 금융 규칙 언어 | 9~12주 | Money, settle, JSON 계약, 제한된 실행 trace | 통화·정산 규칙을 가진 예제와 구조화된 결과 |
| v0.3 규칙 대체 실험 | 13~16주 | 교육용 COBOL 3개 규칙, 차등 테스트, 사용성 평가, 결과 보고 | 일치·불일치와 평가 범위를 재현할 수 있음 |

4주 종료 시 산술식 실행이 안 되면 사용자 함수를 일정 후반으로 옮긴다. 8주 종료 시 기본판 검증이 안 끝나면 Money를 시작하지 않고 기본판을 마무리한다. 최종 v0.3에는 사용자 함수가 포함되어야 한다.

이번 계획에는 반복문, 배열·맵, 클래스, 패키지 시스템, DB 연결, 실제 송금, 자동 환전, 복리·세금·일수 계산 규약, 자동 COBOL 변환기, 바이트코드 VM, JIT를 넣지 않는다. 호스트 Go 코드의 비교·벤치마크 반복은 언어의 반복문 기능과 구분한다.

## 5. 숫자 계약

### 5.1 Decimal 표현

값은 c × 10^(-s)로 표현한다. c는 big.Int인 부호 있는 정수 계수, s는 음수가 아닌 스케일이다.

    12.30  → 입력 해석 (1230, 2) → 정규형 (123, 1)
    -0.003 → (-3, 3)
    -0     → (0, 0)

스케일이 양수인 동안 계수 끝의 0을 제거해 정규화한다. 1.20과 1.2는 같은 값이다. 출력 자릿수는 별도의 FormatAt으로 지정한다. FormatAt은 값을 바꾸지 않으며, 반올림이 필요하면 오류를 낸다.

big.Int를 외부에 노출하지 않는다. 입력 숫자를 바꾸지 않고 새 결과를 반환한다. big.Int를 복제할 때는 Set을 사용한다. [S6]

### 5.2 초기 제한값

| 항목 | 기본값 |
|---|---:|
| 정규화된 계수의 최대 십진 자릿수 | 128 |
| Decimal 최대 스케일 | 36 |
| 반올림·나눗셈의 목표 스케일 | 0~36 |
| 숫자·식별자·문자열 토큰의 최대 바이트 | 256 |
| 소스 파일 최대 크기 | 1 MiB |
| 구문 중첩 깊이 | 128 |
| 평가할 AST 노드 수 | 실행당 100,000 |
| 함수 호출 깊이 | 64 |
| trace 이벤트 수 | 10,000 |

이 수치는 학습용 구현의 초기 설계값이며 금융의 보편적인 최적값이 아니다. 숫자·소스·실행 제한 초과는 자동 반올림이나 포화값으로 바꾸지 않고 진단 코드와 함께 종료한다. trace 이벤트 상한은 예외로, 잘림을 명시하고 수치 계산은 계속한다. 산술의 임시값은 피연산자 한도에서 계산 가능한 범위로 생성하고, 정규화한 결과에 128자리·36스케일 제한을 적용한다. format과 format_money의 자리 인수도 0~36으로 제한한다.

### 5.3 연산

| 연산 | 동작 |
|---|---|
| +, - | 큰 스케일에 맞춰 계수에 10의 거듭제곱을 곱하고 정수로 계산 |
| * | 계수 곱, 스케일 합. 정규화 후 결과 한도 검사 |
| ==, !=, <, <=, >, >= | 값 기준 비교 |
| div(a, b, digits, mode) | 명시한 스케일과 모드로 몫 생성 |
| round(x, digits, mode) | 명시한 자리로 값 조정 |
| format(x, digits) | 정확하게 표현 가능한 경우에만 문자열 생성 |

소스 숫자는 [0-9]+ 또는 [0-9]+.[0-9]+ 형태이며 음수는 접두 연산자로 처리한다. 지수 표기, NaN, Infinity, 숫자 안의 쉼표·밑줄은 제공하지 않는다. 슬래시 연산자는 E_DIVISION_POLICY_REQUIRED를 내고 div 사용법을 안내한다.

문자열과 숫자를 자동 변환하지 않는다. 숫자는 lexer가 보관한 원문에서 직접 해석한다. JSON에서도 금액·이율은 문자열로 받아 같은 파서를 사용하며, JSON 숫자 문자열에는 맨 앞의 선택적 - 부호를 허용한다. encoding/json의 일반 인터페이스 디코딩 과정에서 숫자가 float64가 될 수 있으므로 입출력 계약이 이를 우회하도록 한다. [S7]

### 5.4 반올림

| 모드 | 정확히 중간일 때 | -2.5를 정수 자리로 |
|---|---|---:|
| HALF_EVEN | 마지막 남는 숫자가 짝수인 쪽 | -2 |
| HALF_UP | 절댓값이 커지는 쪽 | -3 |
| TOWARD_ZERO | 버리는 자리와 관계없이 0 쪽으로 절사 | -2 |
| EXACT | 버려지는 값이 0이 아니면 E_INEXACT | 오류 |

HALF_UP의 up을 양의 무한대 방향으로 해석하지 않는다. 절댓값에서 몫 q, 나머지 r, 양의 분모 d를 구해 HALF_EVEN은 2r>d 또는 2r=d이면서 q가 홀수일 때 q를 증가시킨 뒤 부호를 복원한다. HALF_UP은 2r>=d를 사용한다.

round와 div는 같은 내부 반올림 원리를 사용한다. 결과와 함께 Inexact 여부를 반환해 trace에서 확인한다. HALF_EVEN을 모든 업무의 기본 정책으로 숨겨 적용하지 않는다.

검증 예:

    round(2.345, 2, "HALF_EVEN")  = 2.34
    round(2.355, 2, "HALF_EVEN")  = 2.36
    round(-2.345, 2, "HALF_EVEN") = -2.34
    round(9.995, 2, "HALF_EVEN")  = 10
    format(round(9.995, 2, "HALF_EVEN"), 2) = "10.00"
    div(-2, 3, 2, "HALF_EVEN")   = -0.67
    div(1, 3, 2, "EXACT")        = E_INEXACT

두 번 반올림한 결과는 한 번 반올림한 결과와 다를 수 있다. 1.2451을 HALF_EVEN으로 3자리, 다시 2자리로 줄이면 1.24이고 바로 2자리로 줄이면 1.25다. 이를 정상적으로 설명할 수 있어야 한다.

## 6. 언어 문법과 실행 의미

예약어는 let, if, else, fn, return, true, false로 시작한다. 문자열은 처음부터 지원해 반올림 모드를 명시할 수 있게 한다. 문자열 연결과 숫자로의 자동 변환은 제공하지 않는다.

식별자는 ASCII 영문자 또는 밑줄로 시작하고 이후 숫자를 허용한다. 소스는 UTF-8이며 한글은 주석과 문자열에서 사용할 수 있다. 문법의 기본 형태는 다음과 같다.

    let 이름 = 표현식;
    if (Bool표현식) { 문장들 } else { 문장들 }
    fn(매개변수들) { 문장들 }
    return 표현식;
    함수(인수들)

세미콜론은 문장 끝에 쓰되 파일 끝과 블록의 닫는 중괄호 직전에는 생략할 수 있다. else는 선택 사항이다. 접두 연산자는 -와 !이고 !는 Bool에만 적용한다. 논리 AND·OR 연산자는 초기 버전에서 제공하지 않는다. Bool과 String은 같은 타입끼리 ==와 !=만 제공한다. 함수와 Unit의 비교는 오류다.

- let은 한 환경 안에서 재정의할 수 없는 이름을 만든다.
- 블록과 함수는 별도 환경을 사용하며 바깥 이름을 읽을 수 있다.
- 안쪽 블록의 이름 가리기는 허용하고 같은 환경의 중복 선언은 오류다.
- if 조건은 Bool이어야 한다. 숫자를 참·거짓으로 자동 해석하지 않는다.
- if는 문장이다. 함수는 return으로 값을 반환하고 반환 없이 끝나면 E_MISSING_RETURN이다.
- 함수는 선언된 위치의 환경을 참조한다. 재귀는 호출 깊이와 평가 노드 제한을 받는다.
- 함수 인수의 개수는 정확히 맞아야 한다.
- print는 일반 CLI와 REPL에 제공하고 계약 실행의 JSON 출력 모드에서는 거부한다.
- 표현식 문장은 계산할 수 있으나 값이 필요한 계산은 이름이나 return으로 명시한다.

핵심판의 목표 프로그램:

    let simple_interest = fn(principal, annual_rate, years) {
        return principal * annual_rate * years;
    };
    let interest = simple_interest(1000000, 0.05, 0.5);
    print(round(interest, 0, "HALF_UP"));
    print(div(1, 3, 6, "HALF_EVEN"));

이는 문법 초안의 예상 동작 예시이며 실행된 결과를 인용한 것이 아니다.

## 7. Money와 정산

Money는 통화 코드와 Decimal 금액을 갖는다. 초기 통화 코드는 KRW, USD로 제한한다. money 생성 시 소수 자리를 자동으로 자르지 않는다. 원 미만·센트 미만의 계산 중간값을 보존할 수 있다.

| 식 | 결과 |
|---|---|
| 같은 통화 Money + Money, Money - Money | Money |
| 같은 통화 Money의 비교 | Bool |
| Money * Decimal, Decimal * Money | Money |
| div(Money, Decimal, digits, mode) | Money |
| Money * Money | E_TYPE_MISMATCH |
| Money + Decimal | E_TYPE_MISMATCH |
| 다른 통화 Money의 산술·비교 | E_CURRENCY_MISMATCH |
| div(Money, Money, ...) | 초기 버전에서 E_TYPE_MISMATCH |

같은 통화끼리 나눈 비율은 의미를 추가 설계해야 하므로 초기 버전에서 제공하지 않는다. 이율은 0.05 같은 무차원 Decimal로 표현한다.

settle(money, digits, mode)는 최종 지급·청구 금액을 결정하는 자리 줄이기다. KRW는 무조건 0자리, USD는 무조건 2자리라는 숨은 규칙을 넣지 않고 인자로 지정한다. 금액 출력의 0 채우기는 계약의 출력 자리 또는 format_money로 처리하며 반올림을 다시 하지 않는다.

    let interest = fn(principal, annual_rate, years) {
        let raw = principal * annual_rate * years;
        return settle(raw, 0, "HALF_UP");
    };
    print(interest(money("KRW", 1000000), 0.05, 0.5));

정산 위치의 필수 사례는 USD 0.335 세 건이다. 각 건을 2자리 HALF_EVEN으로 정산한 뒤 더하면 1.02이고, 먼저 합산한 1.005를 정산하면 1.00이다. 어느 쪽을 쓰는지는 업무 명세가 결정한다.

최소 통화 단위로 잔여액을 배분하는 함수는 후속 확장이다. USD 100.00을 세 명에게 33.34, 33.33, 33.33으로 배분하는 예와 잔여 1센트 귀속 순서를 별도 명세한다. 배열·배분 함수는 v0.3의 필수 범위에 넣지 않는다.

## 8. 구조와 모듈 경계

소스가 token, AST, 평가 결과로 바뀌는 구조는 교재를 참고하되 금융 숫자 계층은 독립 모듈로 둔다. [S8]

| 모듈 | 책임 | 지켜야 할 경계 |
|---|---|---|
| diagnostic | 오류 코드, 소스 위치, 출력용 진단 | 다른 도메인 모듈에 의존하지 않음 |
| decimal | 정확한 숫자 표현·산술·반올림·포맷 | lexer·평가기·Money를 모름 |
| token, lexer | 원문을 토큰으로 구분 | 숫자를 float64로 변환하지 않음 |
| ast, parser | 우선순위를 반영한 구문 트리 | 실행과 금액 계산을 하지 않음 |
| money | 통화와 숫자의 연산 규칙 | JSON·파일·네트워크에 의존하지 않음 |
| eval | 값, 이름 환경, 분기·함수·내장 함수 | 상태 변경은 실행 문맥 안으로 제한 |
| contract | JSON 입출력과 규칙 경계 | 금액을 숫자 JSON 값으로 중간 변환하지 않음 |
| trace | 실행 근거를 담는 단순 이벤트 | eval의 값 객체를 참조하지 않고 문자열 사본을 받음 |
| cli, repl | 파일·표준 입출력과 실행 조합 | 숫자 연산을 직접 구현하지 않음 |

구체적인 파일과 인터페이스는 구현 계획서에 적는다. Go 표준 라이브러리로 시작하며 일반 Decimal 라이브러리는 런타임 의존성에 추가하지 않는다. 독립된 기준 구현과의 비교에는 별도 도구를 사용할 수 있다.

## 9. 규칙의 입출력 계약과 계산 근거

계약 실행은 소스 파일, main 함수, 계약 JSON, 입력 JSON을 받는다. 계약은 입력 이름·타입·허용 범위·정렬 순서·출력 통화·출력 자리를 정의한다. JSON 입력의 숫자는 모두 문자열이다.

    {
      "schema_version": "1",
      "rule": "interest_v1",
      "inputs": {
        "principal": {"currency": "KRW", "amount": "1000000"},
        "annual_rate": "0.05",
        "years": "0.5"
      }
    }

입력의 알 수 없는 필드, 중복 키, 숫자 JSON 값, 누락 필드, 잘못된 통화와 범위는 거부한다. 출력은 성공 또는 오류의 JSON 레코드 하나다. 진단·진행 메시지는 stderr로 보내고 print는 JSON 모드에서 E_OUTPUT_SIDE_EFFECT로 처리한다.

계약 파일의 고정 구조는 다음과 같다. parameters 배열의 순서대로 main에 인수를 전달한다. 이 버전의 계약 실행은 Money 출력 하나만 허용한다.

    {
      "schema_version": "1",
      "rule": "interest_v1",
      "entry": "main",
      "parameters": [
        {"name": "principal", "type": "money", "currency": "KRW",
         "min": "0", "max": "999999999.99", "scale_max": 2},
        {"name": "annual_rate", "type": "decimal",
         "min": "0", "max": "1", "scale_max": 6},
        {"name": "years", "type": "decimal",
         "min": "0", "max": "10", "scale_max": 6}
      ],
      "output": {"type": "money", "currency": "KRW", "scale": 0,
                 "min": "0", "max": "999999999"}
    }

계약의 min과 max는 경계를 포함하는 수치 비교다. scale_max는 입력 문자열의 실제 소수 자리 개수를 검사한다. 같은 값이어도 소수 자리가 계약보다 긴 문자열은 거부해 입력 필드 형식을 유지한다. 계약에 나타나는 정수 메타데이터인 scale과 scale_max는 JSON 정수이고, 금액·이율·범위 값은 JSON 문자열이다.

성공 출력은 schema_version, rule, status="ok", result={currency, amount}를 갖는다. amount는 출력 계약의 자리로 정확하게 포맷한 문자열이다. 오류 출력은 status="error", error={code, message, file, line, column}를 갖는다. 소스 위치가 없는 계약 오류의 위치는 null이다. 성공 종료는 0, 입력·구문·평가·계약 오류는 1, CLI 사용법·파일 읽기·trace 파일 쓰기 실패는 2다.

출력 타입·통화가 틀리면 E_CONTRACT_OUTPUT, 출력 범위를 넘으면 E_LEGACY_RANGE, 출력 자리로 정확하게 나타낼 수 없으면 E_OUTPUT_SCALE이다. 출력 어댑터가 자동 반올림하지 않는다. 출력 범위 검사 실패를 포함한 오류에서는 정상 금액을 함께 내보내지 않는다.

호스트 CLI만 입력·출력 파일을 다룬다. 언어 자체에 DB, 네트워크, 현재 시각, 난수에 접근하는 내장 함수를 넣지 않는다.

CLI는 인수 없이 시작하면 REPL, -file 경로를 주면 파일 실행이다. -json은 -file, -contract, -input을 함께 요구하며 계약의 entry를 호출한다. -trace 경로는 선택 사항이다. 옵션과 계약을 동시에 주면서 모호한 기본 entry를 추측하지 않는다.

    go run ./cmd/fin -file examples/interest_v1.fin -contract contracts/interest_v1.json -input testdata/inputs/interest.json -json -trace build/interest.trace.jsonl

trace는 다음을 남긴다.

- 규칙 소스의 SHA-256, 계약 버전, 실행기 버전, 입력과 제한 설정.
- 이벤트 순서와 소스 위치.
- 계산한 피연산자와 결과의 정규형 문자열.
- 실제 선택한 조건 분기.
- div·round·settle의 목표 자리, 모드, Inexact 여부.

trace를 켜고 끈 실행의 수치 결과는 같아야 한다. 이벤트 상한을 넘으면 trace_truncated를 명시하고 계산은 계속한다. trace는 평가기가 실제 실행한 내용을 기록하며, 별도로 만들어 낸 설명 문장으로 대체하지 않는다. 이는 학습·디버깅용 계산 근거이며 위변조 방지 감사 시스템을 구현했다는 의미는 아니다.

## 10. 대체성 실험에 사용할 교육용 규칙

실제 은행의 규정이라고 부르지 않는다. 아래 3개는 이 프로젝트가 직접 정의한 비교용 규칙이다.

| 규칙 | 입력과 계산 | 필수 경계 |
|---|---|---|
| 단리 이자 | KRW 원금 × 연이율 × 연 단위 기간, 마지막에 0자리 HALF_UP | 0, 소수 기간, 정확히 절반인 결과, 범위 초과 |
| 구간 수수료 | 1,000,000원까지 0.001, 초과분에는 0.0005를 적용한 누진식, 마지막에 0자리 HALF_UP | 경계 바로 아래·같음·바로 위, 적용 분기 |
| 세 항목 합산 정산 | USD 항목 3개를 먼저 합한 뒤 2자리 HALF_EVEN | 0.335 세 건, 음수 조정 항목, 0 주변 |

수수료는 1,000,000 이하일 때 amount × 0.001, 초과일 때 1000 + (amount - 1000000) × 0.0005다. 단리의 핵심 예는 원금 1,000,000, 연이율 0.05, 기간 0.5에서 이자 25,000이다.

각 COBOL 프로그램은 입력 필드, 중간 필드, 수신 필드, 반올림과 ON SIZE ERROR 경로를 명시한다. 비교 환경에는 cobc --version, 컴파일 옵션, 소스 해시, OS를 남긴다. 실행 파일은 비교 때 한 번 빌드하고 케이스마다 다시 컴파일하지 않는다.

교육용 프로필의 필드는 다음으로 고정한다. 비교하는 컴파일러가 이 선언을 지원하는지 먼저 빌드로 확인하며, 선언을 바꾸면 프로필 버전도 바꾼다.

| 규칙 | 입력 필드와 범위 | 정확한 중간 필드 | 최종 수신 필드와 정책 |
|---|---|---|---|
| interest_v1 | 원금 S9(9)V99, 0~999999999.99; 이율 9V9(6), 0~1; 기간 99V9(6), 0~10 | S9(15)V9(14) COMP-3 | S9(9) COMP-3, HALF_UP, 범위 0~999999999 |
| fee_v1 | 금액 S9(9)V99, 0~999999999.99 | S9(15)V9(14) COMP-3 | S9(9) COMP-3, HALF_UP, 범위 0~999999999 |
| sum_v1 | 각 항목 S9(9)V9(3), -999999999.999~999999999.999 | S9(15)V9(14) COMP-3 | S9(9)V99 COMP-3, HALF_EVEN, 범위 -999999999.99~999999999.99 |

입력의 모든 숫자 필드는 COMP-3를 사용한다. 단리의 소수 자리 수는 2+6+6=14이므로 위 중간 필드에서 자리 손실 없이 표현할 수 있다. GnuCOBOL의 HALF_UP 대응은 NEAREST-AWAY-FROM-ZERO, HALF_EVEN 대응은 NEAREST-EVEN으로 명시한다.

계약이 유효한 입력을 두 구현에 전달하고, 원본 COBOL의 ON SIZE ERROR는 비교 결과의 E_LEGACY_RANGE 또는 E_DIVISION_BY_ZERO로 정규화한다. 계약 자체에서 거절한 입력 수는 별도 집계하며 COBOL 실행 일치 건수에 넣지 않는다. 원금 999999999.99, 이율 1, 기간 10처럼 유효한 입력에서 수신 필드만 넘는 사례도 실행한다.

정상 금액만 비교하지 않고 정상·오류 상태, 오류 분류, 분기, 수신 필드 범위, 출력 자리도 비교한다. 전체 입력 공간의 동치가 증명됐다고 쓰지 않고 실행한 사례 집합에서의 일치율과 불일치 건수를 보고한다.

## 11. 검증 설계

### 11.1 숫자와 언어의 정확성

- 직접 계산한 사례: 0.1+0.2, 1.2+0.003, 0.01×0.01, 음수·자리 올림·반올림 경계.
- 독립 기준: big.Rat로 정확한 덧셈·뺄셈·곱셈을 비교한다. round·div는 Python decimal의 문자열 입력·명시적 모드·충분한 context로 생성한 독립 기준 파일과 값·Inexact·오류를 대조한다. 런타임의 반올림 보조 함수를 정답 생성에 재사용하지 않는다.
- 성질: 한도 안에서 x+y=y+x, (x+y)-y=x, 원래 피연산자 보존.
- 자릿수 경계: 계수 128/129자리, 스케일 36/37, 올림 후 자릿수 초과.
- 오류: 0 나누기, EXACT에서 값 손실, 통화 혼합, 타입 불일치, 잘못된 모드, 인수 개수, 재귀·구문 제한.
- 파서와 입력: 잘못된 숫자, 닫히지 않은 문자열, 아주 긴 입력, 중첩, 중복 JSON 키.
- trace: 켜고 끈 결과 일치, 같은 입력·소스·설정에서 이벤트 순서 재현.

무작위 숫자 사례는 고정 시드와 생성 범위를 기록하고 최소 10,000쌍을 목표로 한다. 같은 내부 반올림 함수를 정답 생성에도 쓰지 않는다. fuzzing은 우선 파싱과 비정상 입력에서 실행하며 발견한 입력을 회귀 사례로 고정한다. [S9]

### 11.2 성능

float64, 문자열 직접 덧셈, 스케일드 인터저 덧셈을 같은 입력 값으로 비교한다. float64는 정확도 조건이 다르므로 속도와 오차를 함께 보고한다. 문자열 방식은 시험한 범위를 덧셈으로 한정해 표현한다.

파싱만, 산술만, 전체 인터프리터 실행을 분리한다. Go benchmark의 ns/op, B/op, allocs/op와 5회 반복 결과를 남긴다. 짧은 금액, 다른 스케일, 긴 계수, 소액 누적을 포함한다. 결과를 사용해 병목을 찾고 필요할 때만 최적화한다.

big.Int를 썼다는 이유로 성능 개선을 단정하지 않는다. 컴파일된 COBOL과 tree-walk 인터프리터의 실행 속도 우위도 미리 주장하지 않는다.

### 11.3 접근성

프로그래밍 경험이 비슷한 참가자 3~5명에게 이율 변경, 수수료 경계 수정, 반올림 모드 변경, 통화 오류 수정 과제를 준다.

DSL과 Python decimal의 올바른 기준 프로그램을 사용하고, 같은 업무 설명·예제·도움 시간을 준다. 풀이 순서를 번갈아 배정하고 가능하면 서로 다른 동등 난이도 숫자를 사용해 학습 효과를 줄인다.

완료 여부, 수정 시간, 잘못된 결과 수, 도움 요청 수, 계산 근거 설명을 기록한다. 작은 표본에서 관찰한 결과로 보고하며 초보 개발자 전체에 대한 우수성을 주장하지 않는다.

COBOL 도구를 확보하지 못하면 v0.2까지 완료하고 v0.3의 비교는 미실행으로 남긴다. 실행 없이 호환을 완료 처리하지 않는다.

설계 변경은 문제 입력, 이전 동작, 원인 가설, 변경, 검증 결과 순서로 기록한다. 미리 정한 실패 서사를 재현하기 위해 비효율적인 구현을 의도적으로 만들지 않는다. 탐색용 구현에서 실제로 확인한 결과를 바탕으로 선택한다.

소개 문안의 제안:

> 금융 계산에서 금액의 단위와 반올림 시점이 드러나도록 Go 기반 인터프리터를 설계한다. 정수 계수와 스케일로 십진수를 표현하고, 통화 자료형과 명시적 정산 기능을 제공한다. 교육용 COBOL 계산 규칙과 동일한 입력을 실행해 결과와 예외 처리를 비교하며, 작은 업무 규칙을 옮길 수 있는 조건을 검토한다.
